주소창에 `https://www.google.com`을 치고 엔터를 누르면 1초도 안 돼서 화면이 뜹니다. 그 짧은 사이에 일어나는 흐름을 한 번 잡아 두면 TCP, HTTP, DNS 같은 주제가 전체 그림의 어디에 들어가는지 보입니다. 그래서 네트워크 정리의 첫 글로 골랐습니다. 일곱 단계로 나눠 따라가 보겠습니다.

## 1. 주소 해석

브라우저는 먼저 입력한 문자열이 URL인지 검색어인지 판단합니다. URL이면 프로토콜(`https`), 호스트(`www.google.com`), 경로(`/`)로 나눕니다.

`http://`로 입력했더라도 HSTS 목록에 있는 사이트라면 브라우저가 요청을 보내기 전에 `https://`로 바꿉니다. HSTS는 "이 사이트는 HTTPS로만 접속하라"는 약속입니다. 구글 같은 큰 사이트는 브라우저에 목록이 미리 들어 있습니다.

## 2. DNS 조회

컴퓨터끼리는 IP 주소로 통신하니 `www.google.com`이라는 도메인의 IP부터 알아내야 합니다. 찾을 때는 가까운 곳부터 봅니다.

1. 브라우저의 DNS 캐시
2. 운영체제의 캐시와 `hosts` 파일
3. DNS 리졸버 (보통 통신사 DNS나 `8.8.8.8` 같은 공용 DNS)

리졸버에도 기록이 없으면 리졸버가 위에서부터 차례로 물어봅니다.

```text
리졸버 → 루트 네임서버    : www.google.com 어디야?
루트   → 리졸버          : .com은 이 서버에 물어봐
리졸버 → .com 네임서버    : www.google.com 어디야?
.com   → 리졸버          : google.com은 이 서버에 물어봐
리졸버 → google.com 네임서버
google → 리졸버          : 142.250.xxx.xxx
```

여러 서버를 돌아다니며 묻는 일은 리졸버가 맡습니다(반복 질의). 브라우저는 리졸버에 한 번 묻고 답을 기다리기만 합니다(재귀 질의). 받은 답은 TTL 동안 캐시해 두니 매번 이 과정을 다 거치지는 않습니다.

## 3. TCP 연결

IP를 알았으면 서버의 443번 포트(HTTPS)로 TCP 연결을 맺습니다. 클라이언트와 서버는 SYN, SYN+ACK, ACK를 주고받으며 서로 보내고 받을 준비가 됐는지 확인합니다. 이 과정을 3-way handshake라고 부릅니다. 자세한 내용은 TCP 글에서 따로 정리하겠습니다.

> [!NOTE]
> HTTP/3는 TCP 대신 UDP 위에서 동작하는 QUIC을 씁니다. 연결 수립과 TLS 핸드셰이크를 한 번에 처리해서 TCP보다 연결이 빨리 맺어집니다.

## 4. TLS 핸드셰이크

HTTPS라면 데이터를 보내기 전에 암호화 준비를 합니다. 서버가 인증서를 보내면 브라우저는 거기에 믿을 수 있는 기관의 서명이 있는지, 접속하려는 도메인과 맞는지 확인합니다. 확인이 끝나면 양쪽이 이번 연결에서만 쓸 대칭키를 합의합니다. 키를 합의하는 데는 비대칭 암호를 씁니다. 그 뒤로 오가는 실제 데이터는 훨씬 빠른 대칭키로 암호화합니다.

## 5. HTTP 요청

연결이 준비되면 HTTP 요청을 보냅니다. HTTP/1.1 기준으로는 이런 모양의 텍스트입니다. HTTP/2부터는 바이너리로 바뀌었지만 담는 내용은 같습니다.

```http
GET / HTTP/1.1
Host: www.google.com
User-Agent: Mozilla/5.0 ...
Accept: text/html
Cookie: ...
```

이 메시지가 서버까지 가는 동안 계층을 하나씩 내려가며 포장이 덧붙습니다.

| 계층         | 하는 일             | 붙는 정보                 |
| ------------ | ------------------- | ------------------------- |
| 애플리케이션 | HTTP 메시지 작성    | 요청 내용                 |
| 전송         | TCP 세그먼트로 나눔 | 출발·도착 포트, 순서 번호 |
| 네트워크     | IP 패킷으로 감쌈    | 출발·도착 IP 주소         |
| 데이터 링크  | 프레임으로 감쌈     | 바로 다음 장비의 MAC 주소 |

마지막 MAC 주소는 최종 서버가 아니라 바로 다음 장비, 보통 공유기(기본 게이트웨이)의 주소입니다. 게이트웨이의 MAC 주소는 ARP로 알아냅니다.

패킷은 공유기에서 통신사 라우터, 인터넷 백본을 거쳐 이동합니다. 라우터마다 도착 IP를 보고 다음에 보낼 곳을 정하니 한 칸씩 건너가는 셈입니다. 이 동안 MAC 주소는 구간마다 바뀌어도 IP 주소는 끝까지 유지됩니다. 집 공유기의 NAT만은 예외로 출발 IP를 공인 IP로 바꿉니다.

## 6. 서버의 처리와 응답

서버에 도착한 패킷은 반대로 포장을 하나씩 벗기며 HTTP 메시지로 복원됩니다.

큰 서비스는 요청이 바로 웹 서버로 가지 않습니다. 로드밸런서가 받아서 여러 서버 중 하나로 나눠 줍니다. 거기서 Nginx 같은 웹 서버가 정적 파일은 직접 돌려줍니다. 로직이 필요한 요청이면 Spring 같은 애플리케이션 서버로 넘깁니다.

응답 형식도 요청과 비슷합니다.

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Cache-Control: private, max-age=0

<!doctype html>...
```

## 7. 화면 그리기

브라우저는 받은 HTML을 파싱해 DOM을 만들고 CSS로 CSSOM을 만듭니다. 둘을 합쳐 레이아웃을 계산한 뒤 화면에 그립니다.

HTML 안에 있는 CSS, JS, 이미지는 다시 요청해서 받습니다. 이때는 이미 맺어 둔 연결을 재사용하므로 DNS 조회와 핸드셰이크를 처음부터 하지 않습니다.

## 정리

| 단계      | 핵심                                     |
| --------- | ---------------------------------------- |
| 주소 해석 | URL을 나누고 HSTS면 https로 바꿈         |
| DNS       | 캐시 → 리졸버 → 루트·TLD·권한 네임서버   |
| TCP       | 3-way handshake로 연결                   |
| TLS       | 인증서 확인, 대칭키 합의                 |
| HTTP      | 요청 전송, 계층별 포장, 라우터를 거침    |
| 서버      | 로드밸런서 → 웹 서버 → 애플리케이션 서버 |
| 렌더링    | DOM·CSSOM → 레이아웃 → 그리기            |

다음 글에서는 3단계에서 넘어간 TCP를 UDP와 비교하면서 자세히 보겠습니다.
